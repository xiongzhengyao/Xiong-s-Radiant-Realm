# I2C 和 I3C 协议详解

I2C 仍然是传感器与 EEPROM 的默认选择；I3C（MIPI）在移动端传感器集线与更高带宽场景里逐渐普及，并强调对 I2C 设备的共存能力。本文从物理层到协议层对比二者，并补充驱动与调试侧的工程笔记。

## 背景：为什么还要关心总线细节

Camera / IMU / 温湿度等器件大量挂在两线总线上。联调失败时，问题往往落在：

- 上拉与总线电容导致边沿过慢
- 地址冲突或 10-bit / 保留地址误用
- 时钟拉伸与主机超时不匹配
- 混挂 I2C/I3C 时模式切换与热接入未处理好

把协议细节吃透，示波器上的波形才能对应到软件状态机。

## I2C（Inter-Integrated Circuit）协议

### 基本概念

- 由飞利浦公司开发的串行通信总线
- 双线制：SCL（时钟线）和 SDA（数据线）
- 支持多主机和多从机
- 同步、半双工通信

### 物理层

1. **电气特性**
   - 开漏/开集输出
   - 上拉电阻（典型值：4.7kΩ，需按电容与速率重算）
   - 标准模式：100kHz
   - 快速模式：400kHz
   - 高速模式：3.4MHz（需注意主机与从机是否真正支持）

2. **总线特性**
   - 最大电容负载：约 400pF（规范量级，实板以眼图/上升时间为准）
   - 最大设备数量：理论 128 个（7 位地址）
   - 实际设备数量受总线电容、地址与时序裕量限制

上拉电阻粗算思路：在目标频率下保证上升时间满足规范，同时灌电流不超过器件规格。

| 场景 | 上拉偏大的症状 | 上拉偏小的症状 |
| --- | --- | --- |
| 边沿 | 上升沿过慢，采样失败 | 边沿陡但功耗与振铃上升 |
| ACK | 偶发 NACK、地址漂移 | 一般较少，但 EMI 变差 |

### 协议层

1. **基本信号**
   - 起始条件（START）：SCL 高电平时，SDA 由高变低
   - 停止条件（STOP）：SCL 高电平时，SDA 由低变高
   - 数据有效性：SCL 高电平期间，SDA 保持稳定
   - 重复起始（Repeated START）：不释放总线连续访问，常用于写寄存器地址后读数据

2. **数据传输格式**

   ```
   START + 地址(7位) + 读写位 + ACK + 数据字节 + ACK + ... + STOP
   ```

   典型「写指针再读」：

   ```
   START + ADDR+W + ACK + REG + ACK +
   Sr    + ADDR+R + ACK + DATA + ACK/NACK + STOP
   ```

3. **时序要求**
   - 建立时间（setup）
   - 保持时间（hold）
   - 时钟频率与高低电平最小宽度
   - 总线释放时间（总线空闲）

### 高级特性

1. **时钟同步**
   - 时钟拉伸：从机拉低 SCL 延长字节间隔；主机驱动需配置超时
   - 多主机仲裁：SDA 线与的输家退出，胜者继续

2. **寻址方式**
   - 7 位地址（最常见）
   - 10 位地址扩展
   - 通用调用地址（General Call）及保留地址段

### 软件栈与驱动实践

在 Linux 上常见路径：

```text
i2c_adapter（控制器驱动）
  └─ i2c_client（板级/DT 实例化）
       └─ i2c_driver（probe/remove、regmap）
```

Device Tree 片段示例（概念）：

```dts
&i2c1 {
    clock-frequency = <400000>;
    status = "okay";

    humidity@44 {
        compatible = "sensirion,sht3x";
        reg = <0x44>;
    };
};
```

用户态快速探测：

```bash
i2cdetect -y 1
i2cget -y 1 0x44 0x00
# 注意：随意写寄存器可能把传感器打进异常模式，量产脚本要白名单
```

使用 `regmap` 时建议统一：字节序、可读/可写范围、cache、易失寄存器表。

### 常见应用

- EEPROM
- 温度传感器
- 实时时钟
- ADC/DAC
- 显示器控制
- Camera Sensor / VCM / EEPROM（CCI 往往是 I2C 兼容控制器）

## I3C（Improved Inter-Integrated Circuit）协议

### 概述

- MIPI 联盟开发的新一代串行通信协议
- 向后兼容 I2C（混合总线是核心卖点之一）
- 更高的性能和更多的功能：动态地址、带内中断、热接入等

### 主要特性

1. **性能提升**
   - SDR 模式：12.5MHz
   - HDR-DDR 模式：25MHz
   - HDR-TSP 模式：33.3MHz
   - HDR-TSL 模式：33.3MHz

2. **新增功能**
   - 热接入（Hot-Join）
   - 动态地址分配（DAA）
   - 带内中断（IBI）
   - 多重突发传输

### 物理层改进

1. **电气特性**
   - 推挽输出（提高速度；部分阶段仍可能配合开漏）
   - 可选上拉电阻
   - 更低的功耗（减少长期上拉直流消耗）
   - 更好的信号完整性（更高速率下仍需严格走线）

2. **总线配置**
   - 支持更多设备（配合动态地址）
   - 更长的总线距离（相对同频 I2C 更有利，但仍受 PCB 约束）
   - 更好的噪声 immunity

### 协议层增强

1. **通信模式**
   - 单数据速率（SDR）
   - 双数据速率（DDR）
   - 三相传输（TSP/TSL）

2. **高级功能**
   - 设备发现
   - 动态地址分配
   - 带内中断
   - 流控制

概念流程：

```text
总线初始化 → 广播 CCC → DAA 分配动态地址
→ 私有 SDR/HDR 传输 → 设备 IBI 请求服务
→（可选）Hot-Join 新设备入网
```

CCC（Common Command Codes）是主机管理总线的标准命令集，驱动开发时要区分「广播 CCC」与「直接 CCC」。

### 应用场景

1. **移动设备**
   - 摄像头相关器件
   - 显示屏辅助器件
   - 传感器集线器（IMU、环境传感器聚合）

2. **物联网设备**
   - 智能传感器
   - 可穿戴设备
   - 环境监测

### I2C vs I3C 对比

| 特性     | I2C      | I3C         |
| -------- | -------- | ----------- |
| 最大速率 | 3.4MHz   | 33.3MHz     |
| 输出方式 | 开漏     | 推挽为主    |
| 地址分配 | 静态     | 动态（可兼容静态） |
| 中断支持 | 额外引脚 | 带内中断    |
| 功耗     | 较高（上拉直流） | 更低        |
| 兼容性   | -        | 向后兼容 I2C |
| 设备发现 | 弱       | DAA / Hot-Join |
| 软件生态 | 非常成熟 | 平台相关，需确认控制器与从机支持矩阵 |

## 混挂与选型建议

1. **选择考虑因素**
   - 速度需求（IMU 高 ODR 批量读 vs 温湿度低频）
   - 设备数量与是否需要热插拔
   - 总线长度与 PCB 拓扑（星型/菊花链、过孔）
   - 功耗要求（可穿戴/常亮传感器）
   - 成本预算与供货（I3C 从机与主机控制器都要齐）

2. **混挂注意**
   - 确认 I2C 器件能否容忍总线更高电压摆率与特定 CCC 广播
   - 主机进入 HDR 前，应保证遗留 I2C 设备不会被误解释
   - 地址规划：静态地址、动态地址与保留地址不要冲突

3. **最佳实践**
   - 合理选择上拉电阻与串联阻尼
   - 注意信号完整性：等长不是目的，上升时间与振铃才是
   - 考虑 EMI/EMC：边沿过快时评估 RC / 布局
   - 预留调试接口：测点、可切换上拉、可断开分支

## 调试技巧

1. **示波器**
   - 同时看 SCL/SDA；确认 START/STOP、ACK 位位置
   - 测量上升时间，反推上拉与电容是否匹配目标速率
2. **协议分析仪**
   - 解析地址、读写、NACK 位置；对齐驱动日志时间戳
3. **软件手段**
   - Linux：`i2cdetect`、trace 事件、控制器错误计数（NACK/timeout/arb lost）
   - 在驱动中区分：地址 NACK（器件未响应）vs 数据 NACK（协议/状态不对）
4. **边界条件验证**
   - 冷启动、热启动、时钟拉伸拉满、总线中途掉电、多主机仲裁（若有）

常见故障对照：

| 现象 | 优先排查 |
| --- | --- |
| 全部 NACK | 电源、复位、地址、电平域、焊点 |
| 偶发 NACK | 上拉/电容、干扰、拉伸超时 |
| 写入成功读取全 0xFF/0x00 | 读流程缺 repeated start；或器件忙 |
| 只有低速可工作 | 上升时间不足；降速只是掩盖布局问题 |
| I3C 枚举失败 | CCC 支持、固件版本、混挂设备干扰 |

## 总结

I2C 以简单可靠覆盖了海量低速外设；I3C 在速率、动态地址、IBI 与热接入上补齐了传感器总线的现代化需求，并尽量兼容存量 I2C 器件。工程上应先保证电气与地址规划正确，再用 regmap/DT 把设备树化；调试时让波形、协议解码与驱动日志三者对齐，问题通常会很快收敛。选型时不必为了「新」而上 I3C——带宽、中断引脚与功耗账算清楚即可。
